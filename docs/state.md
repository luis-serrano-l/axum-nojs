# How state works with no script

A page with no script has exactly three places to keep state: the URL, cookies, and the
server. webonsive uses all three, each for one job.

## 1. The URL holds *what you are looking at*

Open tab, open accordion section, a dialog that should be open on load. These are keys in the
query string with a fixed vocabulary:

| Key | Meaning | Example |
|---|---|---|
| `tab.<name>` | index of the open panel in the tab group `<name>` | `?tab.settings=1` |
| `open.<group>` | open section(s) in the accordion `<group>`, a comma list for `multi`; empty closes all | `?open.faq=2`, `?open.faq=0,2` |
| `step.<wizard>` | current step (0-based) of the wizard `<wizard>` | `?step.signup=2` |
| `per.<table>` | rows per page of the paged table `<table>`; the page links still carry it, so a shared URL shows the same rows | `?per.files=25` |
| `dialog` | id of a dialog rendered open | `?dialog=confirm` |

Every tab title and accordion title is a link that changes *one* key and keeps the others, so
state composes. An empty value is kept in the link (`?open.faq=`) on purpose: it is an explicit
"nothing open" that wins over the cookie, where dropping the key would let the cookie reopen it.
Example: `/settings?open.faq=2&tab.settings=1`. Links are generated by
`UiState::link(key, value)`, never written by hand.

## 2. A cookie holds *what you looked at last*

`UiState` is an Axum extractor. It reads the query string first and the `wo-ui` cookie second,
so a link wins over memory. When a handler returns `(state, markup)`, `UiState` writes the
merged state back into the cookie, but only if the query changed something. Coming back to
`/settings` with no query re-opens the tab you left.

Writing that cookie on a GET is deliberate. It is idempotent and preference-only, which is
what HTTP means by a *safe* method. Application data still changes only through POST.

## 3. The server holds *the data*

Form values, the counter, the theme. They change through `<form method="post">` and the
handler answers with `prg(redirect_to, flash)`: a `303 See Other` plus a one-shot `wo-flash`
cookie (60 seconds). The next GET renders it with `flash(&caps, state.flash())` and, because
the handler returns its `UiState`, clears the cookie in the same response. Reloading the page
does not resubmit and does not show the message twice.

The redirect target carries the UI state: `prg("/settings?tab.settings=1", Some("Saved."))`.
The form sends the tab index as a hidden field so the handler knows where the user was.

## What you lose

- Clicking a `<summary>` beside its title toggles instantly but does not persist; only the
  title link does. Both behaviours are visible in the demo.
- Cookies off: state still travels in links on one page but is forgotten between pages.
- A dialog opened from state is `<dialog open>`: visible, but not modal and without a backdrop.
  Only script can call `showModal()` on load; the `:target` fallback (`#id`) gives the overlay
  look in every browser, so redirect to `#confirm` when you need it.

## Demo

`/settings`: two tabs, a form in each, a flash after save. Save, go to `/`, come back: the
tab, the values and nothing else are remembered.
